# Binding safety and benchmark validation — 2026-11-15

## Recommendation: first production change, after approval

Add **one import-admission guard for ambiguous implicit decision names** at the
existing `import_preview` boundary. Do not change global `Catalog::matches`,
decomposition, evaluation, live acquisition or already installed definitions.

For a **new inferred** decision association:

1. Retain the original source fragment and the inference provenance. Distinguish
   an explicit native ID/user association from an ID generated by compilation.
2. Determine whether the association is supported by an exact ID, normalized
   full name, complete documented alias or vocabulary alias. A singleton returned
   by `matches` is insufficient: that API also returns prefix candidates.
3. If the association is weak, query event-option candidates **separately**, using
   the same current-country context and any genuinely declared parent event.
   An explicitly false parent condition excludes the option; unknown conditions
   stay unknown. Do not infer `original_tag` from the current country or ID prefix.
4. If a compatible event-option candidate remains, report
   `ambiguous_action_kind`/`needs_revision`, preserve the text and all candidates,
   and prevent publication until the choice is resolved. Do **not** choose the
   event answer automatically and do not add a successful completion predicate.
5. Preserve this ambiguity/inference provenance across repeated previews and the
   commit/install re-preview. A generated ID must not become an apparently
   explicit user choice merely because it appears in compiled JSON.

Suggested implementation location is the operational compilation/admission part
of `native/backend/src/import_preview.rs` (after the promotion result, before
`valid`/publication). Keep any helper local to import admission. The exact alias
evidence should come from the same native normalizer/vocabulary/index, not a new
JavaScript or regular-expression imitation of identity matching.

This is a bounded **new-import safety check**, not a repair of old guide data.
It avoids individual phrase rules and leaves all existing run/step keys alone.
The first patch must include reliable provenance handling; an apparent two-line
check that fails on the second preview is not sufficient.
An import with an already installed guide ID must not silently overwrite a
definition attached to saved runs. Treat replacement/repair as a separate explicit
versioned operation; the narrow guard does not authorize such a migration.

## Evidence and impact

The independently rechecked frozen native snapshot has 50 documents, 6,996
prepared steps and 4,451 distinct per-step entity references. Its installed guide,
settings, association, library and vocabulary fingerprint still matches the local
inputs. This is a **frozen-catalog audit**, not a fresh reimport of all Word files
or proof of availability in a live campaign.

`scripts/audit-guide-bindings.cjs` sends 1,009 queries through the **existing Rust
catalog resolver**, using `native/catalog-core/examples/binding_probe.rs`. It
replays attributable source fragments for 645 name-bound references, adds
cross-family probes for 182 decisions, and queries event options separately.
The latter is important: a combined query can return exact matches from another
kind before prefix matches and hide relevant competing tiers.

| Decision diagnostic | Count |
| --- | ---: |
| Source-name replayed decisions | 182 |
| Exact normalized name evidence | 148 |
| Weak/incomplete source evidence | 34 |
| Weak with a compatible event-option rival | **4** |
| Weak without an event-option rival | 30 |

A blanket ban on incomplete names would withhold all 34, including plausible
Spanish Carlist abbreviations. The narrow shadow guard flags four and leaves
178 outside that new block. **Outside the block does not mean proven correct.**

The shadow guard assumes a future inference is known to be implicit. It does not
misclassify the existing saved ID itself as evidence of explicit provenance.
It is diagnostic code only and is never loaded by the application.

The mechanical scan checked all 22 bound event options for parent consistency,

is limited to exposed fields; it is not a semantic audit of every entity.

Across the 645 source-name probes, 119 reproduced bindings have weak/unclassified
match evidence and 61 saved identities are not reproduced by the simplified
source-fragment query. The latter may reflect compound grammar, relative project
names or compiler transformations: they are **not automatically errors**.
Focus/research resolution and production selectors have specialized paths; the
name-fragment diagnostic does not purport to fully reimplement them.

## Backward-compatible step identity strategy

The installed collection already contains **1,003 `--operation-N` child keys in
48 guides and 58 `--note-N` keys in 26 guides**. This is an existing-data problem,
not only a new-import concern. Adding/reordering a child can reuse a persisted key
for a different action. The newly added native tests reproduce this behavior and
show that the evaluator accepts a supplied check by key; CAS/storage revision
checks prevent concurrent writes, not semantic key reassignment.

For future decomposition changes, use this concrete rollout strategy:

1. **Keep all existing keys and meanings pinned for existing runs.** A qualified
   captured definition must have its own immutable definition/adapter version and
   source/catalog fingerprints. Do not substitute today's projection for an
   unknowable historical definition and call that historically verified.
2. Introduce new decomposition as a separate guide-definition revision. Preserve
   the legacy definition if its exact historical projection is unavailable;
   mark migration as unproven rather than rewriting its checks/targets in place.
3. Assign child identifiers once and persist them in a versioned manifest, keyed
   by immutable parent/source identity and a disambiguated source occurrence.
   Positions remain order metadata, not identity. A text hash alone is insufficient
   for repeated phrases and edits. New imports can use persisted opaque child IDs;
   do not recompute them from the child's current position.
4. Keep a parent container/legacy action distinct from its new children. One old
   parent confirmation does not prove any specific new child. New parent completion
   aggregates only explicitly required children, preserves unknown and distinguishes
   start from completion dependencies.
5. Permit progress migration only for a demonstrated one-to-one correspondence
   with equivalent source provenance, action meaning, conditions and dependencies,
   within the same guide/campaign/run scope. In ambiguous or one-to-many cases keep
   legacy progress and initialize new children as unknown, not completed.
6. Apply the mapping atomically with rollback and revision-conflict checks. Include
   manual checks, started state, construction baselines, production records and
   relative-research bindings/history. Never copy all maps by matching key strings.

The proposed first import-admission guard requires **none** of that data migration:
it changes only admission of new unresolved candidates and leaves installed guides
and runtime decomposition untouched. Versioning/migration remains a prerequisite
before subsequently rewriting existing structured meanings.

## Required tests before approving the first production patch

1. Raw Word sources for all four flagged fragments through the **complete** import
   preview: ambiguity is visible, `valid=false`/needs revision, original quote and
   ordering preserved, no event option auto-selected and no positive predicate
   accepted for publication.
2. Preview → preview, preparation → automatic/manual collection commit, and API
   install: inferred IDs retain their weak provenance. Re-preview of compiled
   output must not bypass the guard. A `reviewed` flag alone is not an identity fix.
3. A genuine explicit native ID or explicit user association remains usable after
   ordinary country/role/parent validation; a generated ID cannot masquerade as one.
4. Exact names/aliases/vocabulary aliases, generic War Bonds, Norwegian mines,
   Spanish Carlist abbreviations and a legitimate externally-sent event remain
   unchanged. Unknown original-country/parent conditions stay unknown; known false
   parent conditions exclude their answer. No general foreign-prefix/ellipsis ban.
5. Same-count/key semantic changes remain regression alarms. Existing saved checks,
   started states, baselines and research/production bindings replay without a
   rewritten key/meaning. Parent confirmation never auto-completes new children;
   incompatible campaigns reject old progress.
6. New-import corpus comparison reports individual affected guides, every newly
   blocked/accepted match and unchanged text/IDs. No new confident false match;
   demonstrate the actual full-import impact rather than extrapolating 4/182 replay.

These are acceptance requirements, **not claims that the unimplemented guard
already passes them**. The diagnostic shadow is tested separately from current
production behavior. The 30 remaining weak decision labels, exact-but-wrong names,
idea/decision ambiguities and unsupported recipient conditions remain follow-up
risks; this small first change is deliberately not a universal resolver redesign.
